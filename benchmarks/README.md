# Reproducible arithmetic benchmarks (local:527)

This is an independent harness using only public arithmetic APIs. It has no external numeric or benchmark dependencies. It measures Krogu on JVM, JavaScript/Node, Wasm/Node and the available host Native release target. JVM additionally measures identical expressions using public `java.math` APIs. No implementation source is imported from OpenJDK or another numeric library.

Run from the repository root with Kotlin 2.4.21's `kotlinr` script runner on PATH:

```sh
export JAVA_HOME="$HOME/.sdkman/candidates/java/25.0.4-librca"
export PATH="$HOME/.sdkman/candidates/kotlin/2.4.21/bin:$JAVA_HOME/bin:$PATH"
kotlinr benchmarks/generate-jdk.main.kts --check
kotlinr benchmarks/run.main.kts all benchmarks/results/my-baseline 3 5 5 100
kotlinr benchmarks/check-results.main.kts benchmarks/results/my-baseline
```

Arguments are platform (`all|jvm|js|wasm|native`), a NEW output directory, process forks, warmup batches, measured samples and target batch milliseconds. Defaults are `all`, a timestamped directory, 3, 5, 5, 100. Each measurement calibrates its own operation count to at least half the target duration, capped at 1,048,576 operations. The actual elapsed duration and count are always emitted. More warmup/samples and longer batches should be used for publication or optimization decisions. Raw observations are preserved rather than discarded as outliers.

The runner requires **BellSoft JDK 25.0.4+9-LTS** (override installation directory with `BENCH_JAVA_HOME`) and **Node 26.2.0** (override binary location with `BENCH_NODE`); it rejects other versions. The default Node path is Gradle's `~/.gradle/nodejs/node-v26.2.0-<os>-<arch>/bin/node`. Install that pinned Node if absent. Gradle 9.8.1 is pinned by the wrapper with a distribution checksum, Kotlin and Kotlin/Native are 2.4.21. Node flags are `--expose-gc`; JVM flags are `-Xms256m -Xmx1g -XX:+UseG1GC`. macOS and Linux host Native selection is automatic; unavailable cross-targets are not presented as measured. Windows Native may be built with `:benchmarks:linkReleaseExecutableMingwX64` and measured manually with an appropriate process RSS tool.

`run.main.kts` builds production JS/Wasm and release Native artifacts, then executes binaries directly. Gradle/compiler startup is excluded from arithmetic timing and process RSS. Each fork is a new process. JVM forks alternate Krogu/JDK implementation order. The common harness emits comments plus CSV; `<platform>-<fork>.process.txt` contains `/usr/bin/time` process metrics and stderr. On macOS "maximum resident set size" is bytes; GNU time on Linux reports maximum RSS in KiB. This peak includes runtime, both prepared JVM implementations, warmup/calibration, GC and measurement; it is **not** bytes/op or a peak attributed to a single operation. Commands, environment, Git revision/status, source SHA-256 and binary SHA-256 manifests accompany results. Before/after each fork, host snapshots record uptime/load, memory/swap and processes reporting at least 10% CPU; these are samples, not continuous proof of an idle host. Paths in manifests may refer to the original checkout/cache; source hashes identify the measured state even when its harness had not yet been committed.

## Workloads and interpretation

There are 64 named cases per implementation. All have 16 fixed operands rotating by iteration index. Integers have 9, 77, 309 and 1,234 decimal digits (approximately 30, 256, 1,027 and 4,099 bits); multiply/divide use half-width right operands and square uses the same full-width operand. Decimal cohorts are `123.45`, a 50-digit coefficient, and 20-digit coefficients with exponent +80/-80. Their leading three digits vary from 123 through 138. Context operations use precision 34/HALF_EVEN; round uses precision 7/HALF_EVEN; setScale uses scale 4/HALF_EVEN. Cases cover parsing, string formatting, integer/decimal comparison, decimal precision, multiplication, square by multiplication, division, round, setScale and a multiply/add/divide chain.

Operand creation, contexts and lambda creation happen before measurement. Parsing is included only in explicitly named parse cases. The chain counts as one operation; every latency/throughput figure describes one named expression, not its internal arithmetic steps. Square means `multiply(a, a)`, not a private square kernel. Format/precision cases reuse immutable operands and therefore include warmed caches where the implementation caches these results. They are deliberately steady-state measurements, not cold creation/formatting or creation/hash benchmarks. Add separate names and prepared inputs for such workloads rather than changing the meaning of existing cases. Extend `kroguWorkloads()` with additive `Workload(name, run)` cases; the common harness supports every target. Re-run `generate-jdk.main.kts` after changing mirrored public-JDK expressions; custom non-JDK APIs should use a separate workload provider.

A globally reachable 256-slot result ring receives every result; all slots are hashed after each batch outside timing and their checksum is emitted. Batch counts are multiples of 256, so all fixed operands remain observable. Every fork is checked for stable digests; JVM JDK/Krogu digests must match. This prevents trivial dead-result elimination and also keeps a bounded live result set. Timings include lambda invocation, ring writes, boxing and result escape. The JVM allocation count uses the current thread's `com.sun.management.ThreadMXBean` counter around the batch; it includes those harness costs and excludes allocations on other threads. Unsupported counters are `NA`, never zero estimates. Latency is mean batch ns/op; throughput is its reciprocal, not an independently measured concurrent throughput workload. No contention or multithreaded scalability is measured.

JVM retained heap is total `MemoryMXBean.heapMemoryUsage.used` after `System.gc()`. JS retained heap is Node `heapUsed` after exposed GC. Native retained heap is `GC.lastGCInfo.memoryUsageAfter["heap"].totalObjectsSizeBytes` after `GC.collect()`. Snapshots are outside timing/allocation brackets and include prepared data/runtime/live ring; they are not retained bytes/op. Their units and heap definitions differ across platforms. Wasm reports retained heap and allocations as unavailable: Node heapUsed excludes Kotlin's Wasm linear heap and cannot honestly serve as that metric. Process peak RSS is still recorded. Native/JS per-operation allocation counters are unavailable in this harness. Forced collection requests, runtime caches, background/runtime work and sampling make retained snapshots unsuitable as exact object sizing.

This custom batch harness is a reproducible baseline, not a substitute for JMH-level compiler controls or a statistical claim. Short/capped batches, tiered compilation, GC/safepoints, thermal/load changes, fixed implementation/workload order and warmed result caches can affect observations. Compare within the same platform/run, inspect sample dispersion and repeat on an idle machine before drawing conclusions. JVM is the only direct JDK comparison; cross-platform numbers describe different runtimes. No speedup is claimed, and no absolute timing threshold is used in CI. Correctness remains the arithmetic test suite's responsibility; result checksums are an observability and basic differential sanity check rather than proof.
