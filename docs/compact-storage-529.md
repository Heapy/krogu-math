## Representation and arithmetic argument

BigInteger stores a sign, two Int scalar halves, an explicit representation tag and a nullable wide base-2^30 magnitude. BigDecimal stores its scale, two Int scalar halves, the tag and a nullable wide BigInteger coefficient. Compact instances retain neither a magnitude array nor a coefficient object. The physical scalar fields are Int rather than a retained Long field, so Kotlin/JS does not need a retained emulated-Long object for the payload. This is a source-layout argument; generated layouts and actual costs still need target evidence.

The tag has distinct compact/wide states; Long.MIN_VALUE is an ordinary compact value, not a sentinel. Positive2^63 is wide, negative2^63 is compact. Every normalized wide integer result checks whether its final magnitude fits the signed scalar domain, so both directions use the same canonical boundary. The result of MIN/-1 promotes before signed division; its remainder is zero. Addition/subtraction use the sign-bit overflow identities; multiplication checks the exceptional MIN×−1 pair and verifies the wrapped product by division before publishing a scalar.

Accepted597 composition preserves the bounded immutable10^k metadata table and the volatile/transient lazy decimal precision cache. Cache eligibility reads the representation tag before any coefficient snapshot: ordinary compact precision uses scalar digits, ordinary wide precision uses its stored coefficient, and restored coefficient subtypes retain the uncached route. Constructors/parsers do not seed the cache. Its physical field and any alignment cost belong in both matched baseline/candidate graph measurements.

Accepted535 ingestion uses primitive access only for exact ordinary compact decimals, retaining its old MIN and subtype fallback eligibility. Same-scale sum input checks and stored publication avoid constructing an integer coefficient for the ordinary path; wide expanded working conversion remains separate. Existing budget/atomicity/exact-versus-step semantics remain required.

Compact metadata reads the scalar directly. An explicit `materializeMagnitude()` operation boundary borrows immutable wide limbs or creates a compact scratch view for a selected fallback. It is not a computed words property. Exponent bit loops snapshot their input once. Returned scratch arrays are never mutated as immutable inputs; multiplication's invocation-owned arena remains independent. Wide decimal fallbacks explicitly obtain local snapshots of their source/divisor coefficients; unusual result/conversion/rounding paths may still construct temporary objects. No claim of allocation-free arithmetic is made.

Primitive decimal alignment, multiplication, rounding, setScale, trailing-zero stripping and division publish the original preferred scales. Alignment uses Long differences. Rounding uses a negative-domain coefficient and a finite decimal-power bound, so abs(MIN) and huge shifts do not wrap or force a huge power allocation. Additional carry rounding checks scale before publishing. Optimizations that would bypass required public subclass callbacks are restricted to the exact working class or retain the prior callback prefix. Physical compact eligibility is separate from the older decimal semantic shortcut that excludes MIN.

## Parser and output boundary

The537 lexical/group validation and diagnostics remain unchanged. Its builder starts with a negative scalar magnitude, checks `MIN / power` before multiplication and `MIN + block` before subtraction, then promotes once into owned magnitude scratch. Positive2^63 publishes wide; negative2^63 stays scalar. Direct decimal publication avoids a temporary integer coefficient for an ordinary exact compact text input. Finite-context text keeps its existing rounded decimal scratch and validates rounding/carry/scale first, then publishes a checked negative-domain scalar directly when possible. Wide publication remains unchanged; temporary parsing scratch is not described as allocation-free.

The compact chunk writer divides a negative scalar by a positive radix-group power. It never negates MIN. Three output chunks suffice because a maximal signed-Int group power exceeds2^25 for radix2..36. Wide power-of-two extraction and generic grouped division remain the537 implementation. A stream-restored coefficient subtype retains the legacy virtual output route.

## Current serialization and graph behavior

Normal storage fields remain final. Reading validates the tag, sign, scalar/wide exclusivity, normalized limb domain, public magnitude range and canonical compact boundary. Wide stream-owned arrays are copied before publication, including when a subclass retains an alias elsewhere in the stream. Compact decoding rejects a nonnull wide field; wide decoding rejects unexpected scalar payloads. A restored coefficient subtype may occupy the wide branch even when its stored numeric payload fits Long, preserving its existing virtual behavior and identity. Public constructors still normalize subtype byte encoding before selecting compact storage.

Tests cover compact and wide subclass state, repeated references and cycles, detached wide aliases, impossible tags/fields, constructor byte callbacks, MIN comparison poison callbacks, endpoint promotion/demotion, rounding/cohort boundaries and all-radix537 parser/writer fixtures. These tests are prepared but have not run.
