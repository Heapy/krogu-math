# Independent535 acceptance judgment

Actual task asks a documented safe opt-in accumulator/sum/dot/fma contract, distinct EACH_STEP/FINAL_RESULT semantics, exact independent rounding/cancellation/sign/boundary tests, immutable snapshots, and measurements demonstrating benefit versus ordinary chains and wide-result cost. It does not promise a uniform speedup or an implicit replacement of existing arithmetic.

Executed evidence passes: 29 focused methods (8 JVM/Java,7 each JS/Wasm/macOS),270 raw samples over9 cases and3 fresh remote processes. The independent JSON audit verifies transferred/source/compiler/JDK identities, same-artifact class loading/result/checksum completion, exact sample inventory, timing arithmetic, all summary ratios and procCPU/load context. Existing33 production source files are byte-identical to accepted parent38b2642; only DecimalAccumulator.kt and DecimalSignedWork535.kt are new production sources. No existing arithmetic route is redirected. Documentation changes after measurement are explicitly separate from the frozen numerical sources/tests/script.

Benefit is narrow: equal-scale compact sums are consistently faster (candidate/chain process-median ratios0.131–0.140) and allocate about3% of chain bytes. Mixed sums, wide sums/products and FMA are often much worse: wide sums24.37–26.93x latency, wide dot16.65–17.87x and wide FMA8.09–10.08x in the three processes. These repeatable costs cannot be dismissed as host noise; CPU steal was0.042–0.054% in the before/after snapshots (not an isolation proof). Raw adverse data must remain visible.

Source explains concrete optimization opportunities: DecimalAccumulator.expandedCopy clones all current pages for transactional publication; DecimalSignedWork535.parts converts each input from binary bytes to decimal limbs with a nested byte×limb loop; addProduct performs decimal schoolbook products through mapped/carrying cells; snapshots convert back to binary. Expanded-domain exact semantics and immutable snapshots are valid features, but these measured overhead factors are not mathematically unavoidable. A future checked ordinary-domain or better-owned-workspace path may improve them; no unmeasured threshold or unvalidated arithmetic change is introduced for acceptance.

The literal requirement of demonstrated benefit plus visible wide-result cost is satisfied by the actual specialized opt-in result. No correctness, documented bound or existing-path regression has been found in the reviewed source and finite executed coverage. This accepts the stated specialized scope, not a broad acceleration claim or an exhaustive correctness theorem. Docs must explicitly recommend deciding by workload/policy and identify current implementation overheads rather than presenting25x cost as inherent to final-only rounding. No further rerun is justified solely to improve these numbers.
